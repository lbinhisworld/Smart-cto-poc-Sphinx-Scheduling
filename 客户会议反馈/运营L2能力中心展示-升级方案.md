# 运营 L2 能力中心展示 · 升级方案

> 要解决的不是「库里没有 L2」，而是 **主树只画履约流，能力中心看不见**。  
> 边的定义仍见 [`运营本体生成-升级方案.md`](运营本体生成-升级方案.md) §2、[`运营L3价值流对齐.md`](运营L3价值流对齐.md)。  
> 本波只改展示与只读 API / 卡片栏。不改 `packages/engine/`，不新编能力中心，不把登录角色抬回 L2。禁止写回约定日。

## 1. 为什么单独写

L2 的正职是：**这家厂靠哪几个能力中心把主张兑出去**。现卡已经按这个收了五张（销售承诺、计划可承诺、一部制成、二部制成、仓储齐套），边也齐：

- 能力 `撑住谁` → L1
- 环节 `谁有权` → L2
- 价值流 `撑住谁` → L1；环节 `属于` 价值流

`/kb` 运营左栏却只走「主张 → 价值流 → 环节 → 许可」。主张往下不读权责，卡片也不画「谁有权」。人看见的是缺一层，不是卡没写。

## 2. 本波做什么 / 不做什么

| 做 | 不做 |
|----|------|
| 主张下**并列**两枝：能力中心 / 价值流 | 把价值流改成能力的孩子（会复制流、焊死「一流一中心」） |
| 环节旁标 `谁有权`，点进 L2 | 新写「销售中心 / 生产部 / 总经办」等库外编制 |
| 卡片露出 撑住谁、谁有权、角色、持有、可以、禁止 | 把 `F.l2.role_*` 演示登录抬回权责 |
| CLI `python -m kb tree` 运营段同样并列 | 改 `属于` / `其下` 去迁就树 |
| 未挂主张的能力折起来，像投影 | 自动封印假设能力卡 |

展示分组名「能力中心 / 价值流」只在页面上，**不进 `kb/`、不写成 `属于`**。

## 3. 选定结构：主张下并列，不插进主链

```text
L1 交期是双方的共同约定
 ├─ 能力中心                    ← 展示分组
 │   ├─ L2 销售持有对外约定     （已封印）
 │   └─ L2 计划的倒排与可承诺   （假设）
 └─ 价值流                      ← 展示分组，现树原样
     └─ L3 按单履约价值流
         └─ L3 需求与约定确认
             ├─ 谁有权：销售持有对外约定   ← 芯片，不是孩子卡
             └─ L3 改约定必须走协商
```

同一主张可被多个能力、多条流撑住。同一能力可撑多张主张，于是会在多棵主张树里各出现一次——这是反查，不是复制卡。

不选「主张 → 能力 → 流」单脊：一条履约流同时被销售、计划、一部、二部、仓储撑住，流会在五个能力下各画一遍，看起来像五条生意。

不选「只在环节上挂芯片」：能力中心仍不是一层，扫树还是看不见。

## 4. 树怎么长出来（只读反查，不写新边）

主张节点多一个列表，不进 `其下`：

```text
capabilities(主张) = 层=权责 且 撑住谁 含该主张
children(主张)     = 现有 streams_for_claim（价值流）
```

环节节点多一个列表：

```text
owners(环节) = 谁有权 里能解析到的权责卡
```

`属于` / `其下` 对账测试不动。禁止为了好看给 L1 写上 L2 的 `属于`。

现成对照（不新编）：

| 主张 | 能力中心（`撑住谁`） | 环节上的 `谁有权` |
|------|----------------------|-------------------|
| 交期是双方的共同约定 | 销售持有约定、计划可承诺 | 需求确认→销售；倒排→计划；履约关闭→销售+计划 |
| 按单、不设成品仓 | 计划、一部、二部、仓储 | 制成→一部+二部；齐套许可可挂仓储 |

`F.l1.board_is_meter` / `F.l1.crew_in_sph` 仍降级，不当主张根，也不给它们挂能力枝。

未挂任何主张的权责卡：运营页底折「未挂主张的能力」，与「演示菜单 / 角色投影」分开。登录投影继续只在投影折里。

## 5. 卡片与徽章

L3 是企业层（价值流）。环节、许可是这条流的分解，不是和价值流平级，也不是 L4（L4 留给投影）。

徽章用小数点序号，**不改** yaml 的 `层`（仍写 价值流 / 环节 / 节点），**不改** 卡号（仍 `F.l3.vsm.*` / `F.l3.stg.*` / `F.l3.*`）：

| 层（中文，进库） | 徽章 | 是什么 |
|------------------|------|--------|
| 主张 | L1 | 对外卖什么 |
| 权责 | L2 | 能力中心 |
| 价值流 | L3 | 端到端主链 |
| 环节 | L3.1 | 流上的一站（阶段产出） |
| 节点 | L3.2 | 这一站的许可 / 协议 |
| 投影 | L4 | 文件、菜单、演示角色 |

顾问话术仍按中文层走（「从履约过程上看 / 从这一步上看」），只是树上不再两个相邻节点都写同一个 L3。禁止把 `层` 改成 `L3.1` 字符串，禁止为了对齐徽章去改 `属于`。

运营卡补栏（数据已在 yaml，视图没画）：

- 权责：角色、持有、可以、禁止、撑住谁
- 环节 / 节点：谁有权（可点）、阶段产出
- 主张：反查「谁兑现」= 上面的 capabilities

顾问询问逻辑不改。点 L2 仍只复述已封印命题；假设卡按现规则停或标假设。

## 6. 落地顺序（先测后改）

1. **API / 加载器**：`ops_stream_tree` 主张带 `capabilities`，环节带 `owners`；`card_view` 带出特化栏。`format_ops_tree` 先打能力再打流。测试钉：交期主张下能看到 `F.l2.sales_owns_promise`，菜单投影仍不进主树，`其下` 对账不坏。
2. **`/kb` 运营左栏**：标题改「主张 · 能力 · 价值流」；主张下先能力组、后流组；环节行可点谁有权。
3. **卡片中栏**：按 §5 画栏。

无绑定 Ticket 不改引擎。本波没有新 `kb/` 卡。

## 7. 以后若要变厚（不在本波）

能力中心要加「总经办 / 财务 / 品控」：先有主张、有出处，再交解析员写**假设**权责卡，`撑住谁` 指到主张，相关环节补 `谁有权`。禁止从 `auth.py` 再扫一套角色当能力。
