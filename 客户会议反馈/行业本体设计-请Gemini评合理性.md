## 0. 请你评什么

行业侧（`kb/domain/objects.yaml`，套=行业，栏用「定义」）要回答：

> 巧克力装饰 **MTO 排产** 里有哪些**独立事物**，事物上有哪些**格子**，格子之间如何**构成**。

它**不**回答：谁有权、怎么走流程、哪段代码。那些在运营本体。

我们刚做完两件事：

1. 禁止中性抽象：不能只提取「差异 / 可行性 / 冲突」，必须带本厂语境。
2. 泛化成构成规则：若 B 是 A 的特征 / 槽 / 一次运行的结果，名称必须是「**A 的 B**」，子卡填 `属于: A`，父卡填 `其下`（与加载器按 `属于` 反查对账）。卡片在 YAML 里**平铺**，树靠边还原。槽的编号必须是 `父编号.后缀`。

请验：

1. 这套「独立事物 vs A 的 B」能不能当行业本体的主结构？缺什么边（关联、分类、多端特征）？
2. 现在这棵树是不是被 `models.py` 绑成了「引擎对象树」，而不是「装饰件行业对象树」？该不该拆、怎么拆？
3. 运营若按另一文改成「生意 / 能力 / 流程」，行业树要跟着改绑定规则吗？还是继续只当格子？

## 1. 设计目标与硬约束

### 1.1 要防什么

LLM 做需求时会跳过现场、编主数据（多一个「交期」字段、把枚当版除 SPH、发明第四个组码）。  
行业库的用处：顾问先问**槽在不在树上、封没封印**；工匠 Ticket 必须绑到**最小槽**，禁止发明格子。

### 1.2 故意不做

- 不把 BR 算法写进对象定义（BR-34「先成品后半成品」应在运营许可，对象卡只点名工单）。实践上有几张定义仍漏进了规则，见 §4。
- 不在 YAML 里嵌套整卡（为了以后换图库、每张卡可独立 `prove` / 绑定）。
- 不问无限 why。新卡默认「假设」，人点头才「已封印」。
- 不补冷链仓、机台有限产能、完整工艺路线树。

### 1.3 和运营的交叉

运营「绑哪个对象」必须指向**叶子**（`D.order.due_date`），不能绑 `D.order` 就声称交期槽已封。  
行业变深时，运营**不**改成嵌套树；只改指错层的绑点。

## 2. 生成思路（实际执行过的规则）

### 2.1 出处闭集

对象主要从 `packages/engine/models.py` 的 class / Enum 点名，再对照规格术语（版、组、SPH、工单）。  
覆盖台账要求每个 models 类挂到至少一张卡。  
所以：**先有代码类型，再有行业卡**，不是先有巧克力行业词典再投影到代码。

### 2.2 命名与构成

| 规则 | 含义 | 例 |
|------|------|----|
| 独立事物可单独成名 | 可离开别的东西被指认 | 销售订单、版、组、工单、装饰件品项 |
| B 是 A 的特征 / 槽 / 结果 | 名称「A 的 B」，`属于: A` | 销售订单的客户约定日；倒排计划版本的工单差异 |
| 禁止只留 B | 不要「计划差异」「可行性」 | 曾把 D.diff 从「计划差异」改成带倒排语境的从属名 |
| 槽 vs 对象 | `层: 槽` 不能脱离父存在；`层: 对象` 仍可 `属于`（特征对象） | 约定日=槽；可行性=对象且属于订单 |
| 槽编号 | 必须 `父.后缀` | `D.order.due_date` |
| 特征对象编号 | 可以不改号 | `D.sph` 属于 `D.item`，编号不是 `D.item.sph` |
| 其下 | 父卡列出直接孩子，集合必须等于反查 | 加载器 `load()` 建 `Fact.children`；测试对账 |
| 独立名单（测试白名单） | 无 `属于` 且名称无「的」则必须在此集合 | 销售订单、版、组、工单、装饰件品项、一部成品与二部半成品、装饰件计量单位、一次倒排的输入输出 |

机器门禁：`tests/test_kb_constitution.py`。看树：`python -m kb tree`。

### 2.3 没有单独建模的边

当前只有**构成**（`属于`）。没有：

- **关联**：工单来自销售订单（`source_order_no`）、工单用品项、任务落在组×日。
- **分类**：成品工单 / 半成品工单是工单的两种，不是工单的槽。
- **多端特征**：SPH 同时是「品项 × 组」上的四元组，现在只 `属于 D.item`。

这些关系有的写在说明散文里，没有一等边。

## 3. 现在生成出来的树（`kb tree`）

状态：已封印标 ★，其余假设。

```
★ 销售订单 (D.order)
    ★ 销售订单的客户约定日 (D.order.due_date)     [槽]
      销售订单倒排的可行性 (D.feasibility)       [对象]

★ 版 (D.board)

★ 组 (D.group)
      组的工作日日历 (D.calendar)

★ 工单 (D.wo)
      工单的组日任务 (D.wo_task)

      半成品工单对成品工单的依赖 (D.wo_dep)

  装饰件品项 (D.item)                            [假设根]
      ★ 品项在组上的标准小时产能 (D.sph)
      装饰件品项的单位换算 (D.uom_convert)
      装饰件品项的半成品路线 (D.item_route)

  一次倒排的输入输出 (D.schedule_io)            [一次运行信封]
      一次倒排的齐套占库 (D.kit)
      倒排计划的软约束冲突 (D.conflict)
```

订单卡说明里写还有数量、单位、品项等槽，**结构栏没有收成子卡**。`Order` 模型上还有客户、要货日、紧急、金额等，未点名。

## 4. 我们自己看到的别扭（请评是设计债还是该改）

1. **引擎形状 vs 行业形状**  
   根节点里「一次倒排的输入输出」是算核 I/O，不像巧克力行业对象。齐套快照、五幕回放、计划版本差异都挂在这趟运行下。好理解（一次排程的结果物），但和「销售订单 / 品项 / 工单」不是同一类「行业事物」。要不要把「运行结果」单独成林，不和主数据对象平铺？

2. **订单槽极稀**  
   交期链只封了约定日。数量、单位、品项若永远不收成槽，工匠仍可能发明字段；若全收，又变成 models 字段说明书。粒度停在哪？

3. **定义里掺了运营规则**  
   工单定义写「先排成品再排半成品」；版定义写「枚和盒必须先换成版再算工时」。和方案「对象卡不写 BR」打架。规则应下沉运营许可，还是对象定义允许一句「它是什么尺子」？

4. **SPH 单父**  
   `属于 D.item`，但名称是「品项**在组上**的」。组没有这条孩子。构成边硬塞单父，是否该允许「关联两端」而不假装只有一个 `属于`？

5. **槽 vs 特征对象不稳**  
   约定日是槽；可行性、未放下余量、并线是对象。判别标准我们说「不能脱离父存在的才是槽」，但可行性离开某张订单也能谈「这批单可不可行」。标准够用吗？

6. **工单 ↔ 订单没有构成边**  
   工单不是订单的槽（一张单可多工单，工单可单独指认）。现在两棵树不相连。要不要 `关联: 来自 D.order`，还是靠运营流程表达「接单后展开工单」就够？

7. **成品 / 半成品**  
   没有「成品工单」「半成品工单」两张分类卡，只有工单定义里一句话 + `D.dept`。分类该用「是一种」还是继续用部门对象？

8. **独立名单是白名单**  
   「一次倒排的输入输出」因带「的」可不当独立名单；「一部成品与二部半成品」必须进白名单。规则「有属于则必须带的」会逼出别扭的名字。有没有更好的机器可检规则？

9. **覆盖扫 class 不扫字段**  
   `Order.due_date` 有卡，`qty_order` 没有，台账仍算 Order 已挂。这和「禁止发明槽」是否矛盾？

10. **已封印子卡属于假设父**  
    `D.sph`（已封印）属于 `D.item`（假设）。顾问 `consult(D.sph)` 会通过，问品项整棵树则停。这样对吗？

## 5. 和运营改造的接口（供对照另一篇）

若运营改成 L1 生意 / L2 能力 / L3 流程+许可：

- 行业是否仍只提供「格子」，流程「属于」流程父，不把「倒排发布流程」做成 domain 对象？
- 「一部 / 二部」现在是行业对象 `D.dept`。若 L2 出现「一部的成品制成能力」，是绑 `D.dept`，还是行业侧改名为「斯芬克斯的一部」，避免组织能力和管理实体重名？
- 产品形态（巧克力装饰件）现在主要在 `D.item` 假设卡。L1 若要「生产什么产品」，是复述品项对象，还是运营另写命题、行业只留品项？

我们倾向：**行业 = 有什么东西；运营 = 谁用什么流程把货交出去。** 请确认或否定。

## 6. 请回答的问题

1. **主结构**：只靠「独立事物 + 构成（A 的 B）」是否够做行业本体？必须补哪些边（关联 / 是一种 / 多端）？各举本厂一例，不要泛理论。
2. **两林还是一林**：主数据（订单、品项、工单、组）与「一次倒排的结果物」应否分开？分开后运营绑冲突/插单绑哪边？
3. **槽的闭集**：订单上哪些字段必须先收成槽才允许工匠改代码？给出「必须有 / 可以后补 / 不要收」三列（相对 `Order`：约定日、数量、单位、品项、客户、要货日、紧急、金额……）。
4. **对象卡能不能写规则**：版 / 工单这种「它是什么」和「必须先怎样算」如何划开，避免对象变成 BR 垃圾桶？
5. **SPH**：单 `属于`、双关联、还是升成独立「产能定额」对象？哪种不会让顾问误判「品项封了组上产能就封了」？
6. **命名规则**：继续强制「的」，还是改为「有属于 ⇒ 名称须包含父对象的称呼」？白名单要不要取消？
7. **生成顺序**：继续从 `models.py` 点名，还是应先有一张「装饰件行业最小对象清单」（人写、假设），代码 class 只能挂到清单上的叶子？如何避免又扫成引擎词典？
8. **封印顺序**：`D.item` 未封时，`D.sph` 已封是否应降回假设，或咨询品项时必须展开未封孩子？
9. **最小已封印集**：除现有 6 张外，行业侧还要先封哪几张，顾问才能讲清「一张单怎么变成组日任务」而不编字段？

请用中文层名和「A 的 B」纪律回答。规格没有的客户分群、渠道、冷链仓标「不要收」，不要写成行业对象。
