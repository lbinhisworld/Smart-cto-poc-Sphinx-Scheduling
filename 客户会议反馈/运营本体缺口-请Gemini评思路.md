## 0. 请你评什么

我们有一份**封印知识库**（YAML 卡片 + 有界推理），分两套：

- **行业对象本体（domain）**：巧克力装饰 MTO 里有哪些东西、东西之间的构成（A 的 B）。
- **运营本体（ops）**：号称 L1–L4（主张 / 权责 / 节点 / 投影）。

行业侧最近刚补了构成树（`属于` / `其下`），看起来能自顶向下看见「订单 → 约定日」。  
运营侧梁彬认为**远远不够**，看不出一家企业怎么运营，只看出排程引擎和演示菜单。

请判断：

1. 这个判断对不对？缺口是层定义错了，还是提取范围太窄？
2. 若要对齐「自顶向下看清企业运营架构」，L1 / L2 / L3 各应收什么、不收什么？
3. 怎么改**生成规则**，才能既长出企业运营树，又不把 BR 百科倒进 L1、不现场编造规格里没有的组织？

不要给实现代码。要层定义、提取顺序、和现有卡片怎么改/怎么补的原则。

## 1. 这家厂（已知、可引用，不要发明）

规格与 POC 里已经写明、可以当出处的事实（不是完整 EA）：

- 按单生产（MTO），**没有成品仓**。
- 产品：巧克力装饰件；内部计量**版**，销售常见枚/盒；换算必须走主数据表。
- 生产：一部成品（手工组 / 模具组 / 浇注组）+ 二部半成品；先排成品再排半成品。
- 交期是客户约定日，是销售与工厂唯一共享锚；引擎不得写回 `so_order.due_date`。
- POC 有演示模块 M0–M9（门户、人事、CRM、订单、库存 BOM、生产、财务、项目、排程、品控）和九个登录角色（总经理 / 销售总监 / 业务员 / PMC / 仓库 / 财务 / 人事 / 班组长 / 品控）。这些是**演示投影**，不是正式 SSO、也不是组织编制。

规格里**没有**完整写清：客户分群、渠道体系、销售中心编制、完整 BPMN、报价到回款端到端流程说明书。CRM/合同/品控是 POC 后补页面，多数还没进运营主张。

## 2. 我们现在怎么「生成」本体（思路，不是愿景）

这是实际执行过的生成哲学，不是 TOGAF 教科书。

### 2.1 目标当初是什么

不是先画企业架构再落系统。是：

> 把「为什么这样排、对象有哪些槽、谁有权改什么」从规格 / `.cursorrules` / `models.py` / `auth.py` 收成只读 cold truth，给 Cursor 三角色用，避免 LLM 现场编主数据。

所以生成方向是 **从已有软件资产向上收**，不是从商业模式往下拆。

### 2.2 两套、四层、五条边

| 套 | 栏名 | 层 | 本意（方案原文） |
|----|------|----|------------------|
| 运营 | 命题 | L1 主张 | 生意本身的价值句。禁止倒进行业百科，禁止把 BR-01～50 整表写成主张。特化栏：这根针、为谁、卖的是什么、失败长什么样。 |
| 运营 | 命题 | L2 权责 | 谁持有承诺/计划/现场；可以 / 禁止。POC 无正式 SSO，演示角色要标「演示数据」。 |
| 运营 | 命题 | L3 节点 | **许可动作**，不是流程图框：何时触发、谁有权、只读、可以写、这一步禁止、下一步、业务规则。 |
| 运营 | 命题 | L4 投影 | 落在哪个文件、已做到 / 未实现 / 漂移。不发明新道理。 |
| 行业 | 定义 | 对象 / 槽 | 独立事物可单独成名；B 是 A 的特征则写成「A 的 B」，填 `属于`，父卡写 `其下`。 |

边：撑住 / 细化 / 绑定 / 击败 / 禁止。运营绑行业时必须绑**最小槽**（如 `D.order.due_date`），不绑父对象冒充。

状态：新卡一律「假设」，人点头才「已封印」。`prove` 深度 ≤ 3，假设不得当前提。

### 2.3 收矿闭集（保证「代码没漏挂」，不保证「企业看全」）

台账 `kb/coverage.yaml` 只扫约定清单：

- 规格表里的 BR、冲突码 E1–E10
- `models.py` 的 class
- `packages/engine/*.py`
- `config/*.yaml` 的键
- `auth.py` 的 RoleCode 与 MENU.key
- POC 模块号 M0–M9
- 若干红线测试

刻意不收：seed 数字、vite 配置、讲稿。  
禁止补：冷链、机台 APS、规格没有的工序树。

后果（现在已经发生）：**闭集 100% 不等于企业运营 100%。** 菜单和引擎文件都挂上了卡，但商业模式、客户分群、销售中心、端到端流程可以完全不在闭集里。

### 2.4 批次（按排程主题链，不是按企业价值链）

| 批 | 收的是 |
|----|--------|
| 0 | 交期锚一条链（主张→销售持有→变更审批→禁止写回） |
| A–B | 版尺子、SPH / CREW、两个小时 |
| C–E | 先成品后半成品、齐套、倒排、栅栏涟漪、软冲突 |
| F | **演示角色 + 菜单项 + 产品模块号**（每个 MENU 一条、每个 M? 一条） |
| G | 每个 engine 文件一条投影 |

顾问可 `explain` 的只有三条已封印链：交期、版、CREW。  
页面 `/kb` 只读展示；询问先对意图再对对象名。GUI 不能写库。

### 2.5 行业侧已经改过的生成规则（运营侧没有等价物）

- 特征必须叫「A 的 B」，禁止孤立中性词（不要「计划差异」，要「倒排计划版本的工单差异」）。
- 卡片平铺，层级靠边：`属于` 生成 `其下`。
- 运营**没有**「主张的子主张 / 能力属于哪个部门 / 活动属于哪条流程」这套构成边。运营卡基本是平铺清单。

## 3. 已经生成的数据（盘点）

路径：`kb/ops/*`、`kb/domain/objects.yaml`、`kb/binds/core.yaml`。

### 3.1 L1 主张（3 张，全部已封印）

全部「这根针」都是 **履约**。没有商业模式、客户、渠道、产品组合。

| 编号 | 名称 | 绑 |
|------|------|----|
| F.l1.due_is_shared_reality | 交期是双方唯一的共同约定 | 销售订单的客户约定日 |
| F.l1.board_is_meter | 版是内部唯一计量 | 版 |
| F.l1.crew_in_sph | CREW 口径人数已在 SPH 内 | 品项在组上的标准小时产能 |

命题里偶尔露出生意句（按单、无成品仓、巧克力装饰），但没有独立成卡。

### 3.2 L2 权责（1 张封印 + 9 张假设）

**仅一张真正谈「达成主张的权责」：**

| 编号 | 名称 | 内容 |
|------|------|------|
| F.l2.sales_owns_promise | 销售持有对外约定 | 持有=承诺；可以发起变更；禁止让引擎改约定。角色写成「销售」，不是销售中心/团队。 |

**其余 9 张是登录角色镜像**（`F.l2.role_*`）：总经理、销售总监、业务员、PMC、仓库、财务、人事、班组长、品控。命题几乎都是「这是演示登录角色，不是生产 SSO」。没有：

- 生产部 / 一部 / 二部（作为组织能力）
- 销售中心、销售团队
- PMC 作为计划能力（只有演示角色卡）
- 能力与主张的「撑住」边（除销售持有→交期主张）

### 3.3 L3 节点（名不副实）

方案写的是「许可动作，不是流程图」。落地分成三类，**都不是端到端运营流程**：

**A. 排程许可节点（8）** — 最接近「活动」，但仍是引擎步骤：

| 编号 | 名称 | 状态 |
|------|------|------|
| F.l3.due_change_via_approval | 改约定必须走变更审批 | 已封印 |
| F.l3.normalize_to_board | 数量先归到版再算 | 已封印 |
| F.l3.sph_and_hours | SPH 口径与两个小时 | 已封印 |
| F.l3.finished_then_semi | 先成品后半成品 | 假设 |
| F.l3.kitting | 齐套占库 | 假设 |
| F.l3.backward_place | 从约定日倒排落位 | 假设 |
| F.l3.fence_ripple | 栅栏涟漪与死区 | 假设 |
| F.l3.soft_conflicts | 冲突只提示并给最快日 | 假设 |

**B. 产品模块切片（10）** — `F.l3.mod_M0`…`M9`：命题是「POC 模块 Mx 是演示产品切片」。不是接单、不是排产、不是出货流程。

**C. 菜单项（约 34）** — `F.l3.menu_*`：首页、待办、CRM、订单、排程、品控各页……命题是「演示菜单某某」。这是覆盖台账为了 MENU.key 不漏挂，**不是流程活动**。

缺失的流程例子（用户认为必须有，库里没有独立流程卡）：

- 核心：获客 / 报价 / 接单承诺 / 主数据维护 / 倒排与发布 / 插单改单 / 领料齐套 / 报工入库 / 交期协商 / 出货 / 对账回款
- 支撑：人事出勤→产能、品控来料、金蝶同步、变更审批（变更审批只有「改约定日」这一刀，没有订单变更主流程）

### 3.4 L4 投影

- 红线：禁止写回约定日；组码规格 vs 代码漂移。
- 每个 `engine/*.py` 一条模块投影。
- 结论 3 条：只给最快可交不改日；先归到版；CREW 不再乘。

绑定边几乎全在交期槽上（`binds/core.yaml`）。

### 3.5 行业对象（对照：这侧反而更像树）

已封印根：销售订单、版、组、工单；槽：销售订单的客户约定日；SPH 属于品项。  
其余（品项、换算、BOM、齐套、日历、任务、冲突、插单、计划版本、可行性、五幕……）多为假设，但已用「A 的 B」挂在父对象下。

`python -m kb tree` 能看出订单 / 工单 / 一次倒排三棵构成树。  
**运营没有对应的 `tree`。**

## 4. 梁彬的判断（请直接反驳或补全）

1. **L1 不足**：主张层应能看见客户的商业模式、客户分群、渠道、生产的产品等。现在只有履约计量三条，而且像排程约束口号。
2. **L2 不足**：权责层应包含达成主张的**核心业务能力 / 组织**（生产部、销售中心、销售团队等）。现在是演示登录角色清单 + 一张「销售持有约定」。
3. **L3 不足**：应是**运营流程层**，必须包含核心流程和支撑流程。现在是引擎许可 + 菜单/模块台账，看不出企业怎么转起来。

总评：运营本体没有起到「自顶向下看清企业运营架构」的作用。行业对象有构成，运营没有。

## 5. 我们自己看到的张力（请一并评）

| 张力 | 说明 |
|------|------|
| 闭集 vs 企业全景 | 现在用「代码/菜单扫全」证明无遗漏。若 L1 要商业模式，出处从哪来？规格没写的能不能标「假设」向客户确认？ |
| L3「节点」vs「流程」 | 方案原句是许可动作，不是 BPMN。用户要把 L3 改成流程层。是改层定义，还是 L3 流程、另留「许可节点」给引擎？ |
| 演示角色 vs 组织能力 | `auth.py` 的 SALES / PMC 不能当成销售中心、生产部。要不要拆成两套：能力（真运营）/ 演示投影（现有 role_*、menu_*）？ |
| 主张纯度 | 已立过「不要把 BR 写进 L1」。商业模式卡算主张，还是另一条「企业」轴？会不会 L1 膨胀成公司简介？ |
| 和行业对象的分工 | 「生产产品」是 L1 主张，还是行业对象「装饰件品项」？客户分群有对象吗，还是只有运营命题？ |
| 不问无限 why | 第一期故意有界。企业架构若向下拆流程，边界停在哪，才不会假设繁殖？ |

硬约束请尊重：

- 禁止写回订单约定日。
- 禁止为了圆树而改 `packages/engine/`。
- 规格没有的东西可以假设，不能当成已封印，也不能编冷链/机台 APS。
- 运营绑行业仍应绑到具体槽，不要绑「整个订单」了事。

## 6. 请回答的问题

1. **层定义**：若目标改为「自顶向下看清这家厂怎么运营」，你建议 L1 / L2 / L3 / L4 各叫什么、各收什么粒度？现有「主张 / 权责 / 许可节点 / 代码投影」哪些保留、哪些改名、要不要加「能力 / 流程 / 组织」层？
2. **生成顺序**：还应该从代码往上收，还是必须先铺 L1 企业命题再往下挂现有排程链？两套并行怎么避免两套百科？
3. **现有卡片怎么处置**：34 张菜单卡、10 张模块卡、9 张演示角色——降到 L4 投影、标「演示」、还是删除出运营主树？
4. **L1 最小集**：就斯芬克斯已知事实，主张层最低要有哪几张卡才算「看清商业」？请列名称级，不要写长文。指出哪些必须向客户确认（假设），哪些规格已够封印。
5. **L2 最小集**：能力 / 组织怎么命名才不是中性词（对标我们行业侧「A 的 B」）？例如能不能写「斯芬克斯的销售承诺能力」而不是「销售」？
6. **L3 最小集**：列核心流程 + 支撑流程名单（名称级）。每条流程与现有许可节点（倒排、齐套、改约定）如何「属于 / 其下」，避免流程和引擎步骤平铺打架。
7. **门禁**：怎样证明「企业运营树收全了」？现有 coverage 扫代码不够的话，闭集应该改扫什么（价值链清单？客户纪要章节？），才不会又变成感觉收全。
8. **顾问产品**：`/kb` 若要画出运营树，父卡需要什么字段（对标 domain 的 `属于`/`其下`）？

请用和我们同样的纪律：中文层名、先结构后说明、能标假设就标假设。优先给**可执行的提取规则**，其次才给理论框架名（TOGAF / 价值流 / 能力地图请落到我们四层或你建议的新层上，不要只丢框架名）。
