# 封印本体知识库与三角色 · 升级方案

> 第一期：在仓库里封印运营本体 × 行业本体，并在 Cursor 内启用解析员 / 顾问 / 工匠。不改倒排引擎（BR-27），不加 GUI，不上 Neo4j / LangGraph。

## 1. 目标

把「为什么这样排、对象有哪些槽、谁有权改什么」收成一份只读 cold truth。客户侧永远是结果 + 原因；写入只走开发环。

## 2. 两套本体、一套库

- **运营本体**：这家厂怎么把货交出去——主张、权责、许可节点、代码投影。
- **行业对象本体**：巧克力装饰 MTO 里有哪些格子与量纲（版、组、SPH、墙钟、人·时、工单、订单约定日）。怎么提取见 [`行业本体提取-升级方案.md`](行业本体提取-升级方案.md)。
- 用「撑住 / 细化 / 绑定 / 击败 / 禁止」连起来。不是两套互不说话的百科。

## 3. 卡片

给人看的栏一律中文。顺序：结构栏在上，**说明在最底下当整卡备注**。运营卡用「命题」，行业对象卡用「定义」；`说明` 不替代这两栏。

编号可给机器用；`spo` 等词不出现在编辑视图。

## 4. 推理

文件不会自己推理。`packages/sealed_kb` 的 `prove` 从结论往回走已封印的边（撑住 / 击败 / 绑定），深度 ≤ 3。假设不得当前提。`explain` 把仍活着的「对外怎么说」拼成中文。

不做最短路、不补新边。以后换 Neo4j 只换存放；LangGraph 只编排三角色，不替代库。

## 5. 三个角色（Cursor 内）

| 角色 | 做什么 | 禁止 |
|------|--------|------|
| 解析员 | 从规格/纪要/代码收矿到 `kb/`，交付 L1→叶子假设链；`harvest-check --确认` 才算完成 | 改 `engine/`、直接封印、编库外战略 |
| 顾问 | 先判原理/质疑/细节，再 `ask` / `explain` 已封印链 | 编造主数据；质疑时改库或构拟新规则 |
| 工匠 | 只接绑定过的 Ticket | 发明槽或环节；写回约定日 |

## 6. 第一期范围

种子先跑通**交期锚一条链**（订单.约定日 → 主张 → 销售持有 → 变更审批 → 代码不得写回）。版 / 组 / SPH / 工单只点名对象，不抽完 BR 全集。

落地位置：`kb/`（卡片）、`packages/sealed_kb/`（推理）、`.cursor/agents/`、`.cursor/rules/`。

## 7. 怎么测、怎么用

```bash
.venv/bin/pytest -q tests/test_kb_*.py
.venv/bin/python -m kb explain C.give_earliest_keep_due --情境 按单,无备货,有客户约定,E2 --角色 销售
.venv/bin/python -m kb ask "为什么排程不能改订单交期" --角色 销售
.venv/bin/python -m kb harvest-check F.l3.due_change_via_approval --确认
```

打开 `kb/` 目录读卡片。问为什么用顾问或 CLI。收知识用解析员（只出假设）。改代码先顾问再工匠。
