# 运营本体生成 · 升级方案

> 替代「从菜单和 engine 文件往上扫就当运营架构」的做法。  
> 结构已定：见 [`运营L3价值流对齐.md`](运营L3价值流对齐.md)。  
> 行业如何生成：[`行业本体提取-升级方案.md`](行业本体提取-升级方案.md)。评稿：[`行业本体设计-请Gemini评合理性.md`](行业本体设计-请Gemini评合理性.md)。  
> 不改 `packages/engine/`，不自动封印，禁止写回约定日，禁止补冷链 / 机台 APS。

## 1. 目标

生成出来的运营库必须能**自顶向下看见这家厂怎么兑现承诺**，而不是看见 POC 菜单和算核函数表。

三件事：

1. **骨架**：L1 价值主张 → 至少一条 L3 价值流 → 环节 → 支撑/许可。  
2. **归位**：已有交期/版/CREW 链和 8 张排程节点挂进环节；菜单、模块号、演示角色降到 L4。  
3. **以后怎么收**：每次客户输入交付一条 **L1→L4 垂直解释链**，人点头才算更新完成；禁止再平铺一张 L3 根节点。

失败形态：又扫一轮 `MENU.key` 当流程；把 Git 改动记成孤立 Fact；或为第二条 VP 编茶饮巨头 / 冷链直发 / 过敏原战略。

## 2. 层与边（生成时必须遵守）

| 层 | 中文 | 收什么 | 不收 |
|----|------|--------|------|
| L1 | 主张 | 对外卖什么、不靠什么库存、失败长什么样。特化栏照旧。 | BR 公式、CREW 乘法、菜单 |
| L2 | 权责 | **能力**：谁兑现哪条主张（销售承诺、计划排产、一部制成、二部制成）。名称用「组织或职能 的 权责」。 | `auth.py` 登录账号（那些是 L4） |
| L3 | 价值流 | 兑现某条 VP 的端到端主链。一张流一张卡。`撑住谁` → L1。 | 单步算法、页面路由 |
| L3 | 环节 | 价值流上的一站，有阶段产出。`属于` 价值流。 | 把整条流写成一个环节 |
| L3 | 节点（许可） | 门禁/算法协议：何时触发、谁有权、可以写、禁止。`属于` 环节。现有 `F.l3.normalize_to_board` 等属此类。 | 菜单、模块切片 |
| L4 | 投影 | 文件、BR 号、演示角色、MENU、M0–M9。`落实的是` 指向上层许可或环节。 | 新命题 |

边（只中文，不要 `VALUE_STREAM` / `realizes_*`）：

- 价值流 `撑住谁`：L1  
- 环节 / 许可 `属于`：父卡编号  
- 父卡 `其下`：与加载器按 `属于` 反查一致  
- 许可 `绑哪个对象`：行业**最小槽**  
- L2 `撑住谁`：L1；环节 `谁有权` 可指向 L2  

卡片平铺。产出边仍是：价值流 `撑住谁` L1，环节 `属于` 流。展示上主张下并列能力中心与价值流，见 [`运营L2能力中心展示-升级方案.md`](运营L2能力中心展示-升级方案.md)。禁止为了好看给主张写上权责的 `属于`。

一条已封印 VP **至少**一条价值流。一条流可撑住多张 L1。一张主张也可被多条流兑现。不要一主张一流机械对称。新流必须有主张、有出处；禁止无主张开打样/库存/工艺空流。

## 3. 生成顺序（双向咬合）

不要只从代码逆向，也不要空画 EA。

```text
1. 人定 L1 最小集（规格够的才准封印）
2. 为已封印 L1 建一条价值流 + 四个环节（先假设）
3. 把已有许可节点改「属于」对应环节，补其下
4. 缺的许可（报工考勤、欠产回池）标假设占位，出处写 POC 文档
5. 演示角色 / 菜单 / 模块改层为投影，台账挂点保留
6. 人点头后才把 L1 新卡、价值流升封印；许可随原链
```

解析员：只写 `kb/`。见 §3.1，先交解释链再写卡。  
顾问：验链能否 `explain`；上半截未封或边断则缺前提。  
工匠：只接**用户已认可的链**上的 Ticket；仍绑行业槽 + 许可编号。

## 3.1 每次变更：垂直解释链（解析员主职）

本体更新的最小交付物不是一两个点，而是一条从主张贯通到投影的**支撑链**。客户永远抛 L3/L4 表层动作；解析员必须自顶向下给出正当性，而不是记流水账。

```text
客户输入（需求 / 改代码）
        │
        ▼
已有 L1 能否解释？
   ├─ 能：路径 A — 复用主张/价值流/环节，只提案新叶子
   └─ 不能或打架：路径 B — 张力（拒收伪需求并反问）
                    或整条新链标假设（禁止编库外战略）
        │
        ▼
向用户展示整条链（人话 + 编号）
        │
   用户点头 = 理解对齐
        │
        ▼
写入 kb/：新卡皆假设 + 边（撑住/属于/绑定）
人另一步才封印。禁止「一点头整链改成已封印」。
```

对齐提案必须写清：L1 哪张、L2 谁持有、落在哪个环节、新许可是什么、绑哪个槽、将落在哪个文件。  
例：自动改约定日 → 与 `F.l1.due_is_shared_reality` / `F.l2.sales_owns_promise` 打架 → 张力，改为最快日 + 审批，不入库自动改日。  
例：换色清线 45 分钟 → 旧 L1 若撑不住「为何不能压缩」，停下来问用户是损耗还是品质红线；**不要**现场颁发「过敏原合规」主张。

`harvest_complete`：存在从某张主张到本次叶子的边路径，且用户已确认理解。无路径 = 本次本体更新未完成。顾问交来的质疑：只把用户指出的断裂点收成假设链给人看，禁止顾问或模型直接写卡。

## 3.2 顾问询问分流（原理 / 质疑 / 细节）

`python -m kb ask` 先闭集分类，再定锚，三种意图共用同一条已封印 `prove` 链：

| 意图 | 包装 |
|------|------|
| 原理 | L1→A 分层证明 |
| 质疑 | 同一条链 + 请用户指出断在哪一层；不改库、不构拟新规则 |
| 细节 | 点 A 命题/出处在前，链在后 |

话术只许卡上已有句子。`内部返工` → 交期锚不适用，不是 BR-27 例外。新前提走 §3.1 解析员。

## 4. 本厂第一棵树（生成清单）

本厂已封印的合成 VP（按单零仓 + 约定日是锚）先由一条履约流兑现。**可以**再为其他已对齐的主张建新流；**不生成**无出处的大客户打样流。

### 4.1 L1

| 编号 | 名称 | 状态 | 出处 |
|------|------|------|------|
| F.l1.due_is_shared_reality | 交期是双方唯一的共同约定 | 已有封印 | 规格 |
| F.l1.mto_no_fg_stock | 按单交付装饰件、不设成品仓 | **待建**，规格够可封印 | 规格 §1/§3。命题禁止写冷链原因 |
| F.l1.board_is_meter | 版是内部唯一计量 | 已封印；**降为许可的撑住对象，不再当 VP 主叙事** | 可保留卡，改 `撑住谁` 到履约流「需求」环节，或注明从属尺子 |
| F.l1.crew_in_sph | CREW 人数已在 SPH 内 | 已封印；**降到倒排环节下的许可叙事** | 不删，避免 `explain` 断 |

客户分群、渠道：**不建卡**，直到纪要出现。

### 4.2 L2（假设起步，名称「A 的 B」）

| 建议编号 | 名称 | 撑住 | 不要写成 |
|----------|------|------|----------|
| F.l2.sales_owns_promise | 销售持有对外约定（已有） | 交期锚 | 已够，不必改名「销售中心」才能用 |
| F.l2.cap_plan | 计划的倒排与可承诺能力 | 交期锚、按单零仓 | 不要「PMC部」已封印 |
| F.l2.cap_dept1 | 一部的成品制成能力 | 按单零仓 | 绑 `D.dept`，编制假设 |
| F.l2.cap_dept2 | 二部的半成品制成能力 | 按单零仓 | 禁止写原料组/生巧组 |
| F.l2.cap_kit | 仓储的齐套占库能力 | 按单零仓 | 可选后补 |

`F.l2.role_*`：**改层为投影**，命题保留「演示登录」，不进价值流树。

### 4.3 L3 价值流与环节（待建假设）

**价值流** `F.l3.vsm.order_to_delivery`  
名称：按单履约价值流  
撑住谁：`F.l1.due_is_shared_reality`、`F.l1.mto_no_fg_stock`  
其下：下列四环节。

| 环节编号 | 名称 | 阶段产出 | 谁有权（L2） | 挂入的已有许可 |
|----------|------|----------|--------------|----------------|
| F.l3.stg.demand | 需求与约定确认 | 约定日进系统，数量能说到版 | 销售持有约定 | `due_change_via_approval`、`normalize_to_board` |
| F.l3.stg.schedule | 倒排与齐套锁定 | 贴约定日的计划 | 计划能力 | `backward_place`、`finished_then_semi`、`kitting`、`fence_ripple`、`sph_and_hours` |
| F.l3.stg.make | 双部制成与报工 | 组日任务落下，欠产能回池 | 一部/二部能力 | **待建**报工考勤上限、未完回池（出处：POC 范围说明） |
| F.l3.stg.fulfill | 履约关闭 | 最快日或交付，不改锚 | 销售 + 计划 | `soft_conflicts` |

打样、合同回款：仅当支撑流程假设，`属于` demand 或 fulfill；不得无出处升 VP。要另开价值流必须先有主张并写 `撑住谁`。

出货温控、回款催收：规格不足则环节说明写「缺口」，**不建许可**。

### 4.4 旧 L3 处置

| 现卡 | 生成动作 |
|------|----------|
| 8 张排程节点 | 保留编号与命题；加 `属于` 上表环节；补父卡 `其下` |
| `F.l3.menu_*` | 层改为投影；说明「演示菜单」 |

| 新许可 | 必须先有所属环节，禁止再出现无 `属于` 的 L3 根 |

### 4.5 L4

原投影不动。`落实的是` 尽量补到许可编号。coverage 继续挂 MENU / Role / 模块资产到这些投影卡。

## 5. 提取规则（解析员清单）

遇到一段纪要或一段代码时，按序问，答不上就停：

1. 这是**生意句**还是**算法/页面**？生意 → L1（已有类似卡则补边，不新开）。算法 → 许可。页面 → L4。  
2. 它兑现哪张 **已有或本批在建的 L1**？没有对应 VP → 不建价值流，只标缺口。  
3. 它落在哪个**环节**？写 `属于`。新环节必须先属于已有价值流。  
4. 名称：能力/支撑用「A 的 B」；禁止孤立「插单」「可行性」。  
5. 绑行业叶子槽。没有槽 → 先行业假设槽，或顾问停。  
6. 规格没有的组织名、客户分群、冷链、六组：**不写卡**。  
7. 新卡状态=假设。`explain` 用的旧封印卡编号不改。

禁止：

- 冷链、温控仓、机台 APS、原料组/生巧组、茶饮巨头第二条流、SCOR 五段硬门禁。  
- 把 BR 全文贴进 L1。  
- 为对称给每张主张复制一条价值流。

## 6. 双轨闭集（证明收全）

**软件轨**（已有 `kb/coverage.yaml`）：BR、E 码、engine 文件、config 键、Role、MENU、M0–M9。菜单资产仍挂 L4 投影。不删台账行。

**运营轨**（新建 `kb/ops/value_streams.yaml` 或 coverage 里一类「价值流」）：

```yaml
- 价值流: F.l3.vsm.order_to_delivery
  兑现: [F.l1.due_is_shared_reality, F.l1.mto_no_fg_stock]
  环节: [F.l3.stg.demand, F.l3.stg.schedule, F.l3.stg.make, F.l3.stg.fulfill]
```

测试：每张已封印 L1 ∈ 某价值流的 `撑住谁`；每个环节有 `其下` 或说明含「缺口」。  
不扫 SCOR，不要求采购/退货 100%。

## 7. 批次（只运营，可与行业批次并行）

| 批 | 做什么 | 验收 |
|----|--------|------|
| O0 | schema：层增加价值流/环节；运营 `属于`/`其下`；tree 能打运营 | 测试：其下=反查 |
| O1 | 建 `mto_no_fg_stock`、价值流、四环节；8 张节点挂上 | `kb tree` 看见主张→流→环节→许可；交期/版/CREW `explain` 仍绿 |
| O2 | `role_*` `menu_*` `mod_*` 改层投影 | coverage 不裂 |
| O3 | L2 能力假设卡；环节填谁有权 | 顾问问「谁能改日」能指到销售持有 |
| O4 | 报工/回池许可假设；打样/回款仅支撑假设 | 制成环节不再空白，或说明缺口 |
| O5 | 人封印：按单零仓、价值流（环节可仍假设）；加载器按主张列出其下全部价值流 | 已封印主叙事 L1 均有流；多主张多流有测试 |

O0–O5 已写入 `kb/ops/`。履约流已封印；环节与多数许可仍假设。多家主张、多条流由 `撑住谁` 展开，不要求一主张一流。

## 8. 怎么测、怎么用

```bash
pytest -q tests/test_kb_*.py
python -m kb explain C.give_earliest_keep_due --情境 按单,无备货,有客户约定,E2 --角色 销售
python -m kb ask "为什么排程不能改订单交期" --角色 销售
python -m kb harvest-check F.l3.due_change_via_approval --确认
python -m kb tree
```

`/kb`：运营包按价值流树展示，不默认列出全部菜单投影。询问先对 VP/环节，再对许可。

变更双胞胎：改引擎许可逻辑 = 改对应节点 + 确认仍 `属于` 原环节；新页面只加 L4，不加 L3 根。
